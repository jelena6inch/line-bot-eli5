架構解說 · 給工程師

用一張試算表當資料庫，
做一個 LINE 值日生提醒機器人

「園地小秘書」是大綠地辦公室 15 人 LINE 內部群組裡的機器人，它的工作主要是及時提醒，目前主要任務是：提醒本週的值日生，下班前記得倒垃圾、關窗戶。它在固定時間 @ 值日生，或私訊本人，不用再靠誰記得去喊人。整套沒有自己的伺服器、沒有資料庫：Google Sheets 是資料層兼後台，Apps Script 同時跑 webhook 和排程。這頁說明它怎麼運作、為什麼這樣設計，以及它取捨掉了什麼。

01

需求很小，限制才是重點

功能本身一句話講得完：每週輪一個值日生，每天 16:00 提醒他倒垃圾、關窗戶。難的是下面這幾個限制，它們決定了後面每一個設計選擇。

💸 零預算

用免費的 LINE 官方帳號（每月 200 則推播）和 Google Workspace 內建的 Apps Script。不開 VM、不用 Cloud Run、不買資料庫。

🧑‍💼 非工程師維護

日常操作的人是營運主管，不是工程師。換值日生、加國定假日、查發送失敗，都要能在試算表裡完成，不用碰程式。

📏 額度很緊

LINE 對群組推播按群組人數計費：在 15 人群組發一則算 15 則。每天在群組 @，一個月就超過 200 則。

所以核心設計是混合投遞：週一在群組 @（讓大家都知道這週輪誰），週二到週五改私訊本人（一次只算 1 則）。沒加機器人好友的人沒辦法私訊，就自動退回群組 @。
02

架構總覽：一個 Apps Script，兩個進入點

同一支 Code.gs 綁在試算表上，有兩條完全獨立的執行路徑：

被動 Webhook 路徑

LINE 把事件 POST 到部署好的 Web App 網址。負責「認人」：機器人被拉進哪個群組、誰報到了、誰加了好友。結果寫進「成員名單」和「設定」。

主動 排程路徑

Time-driven trigger 每 5 分鐘跑一次，讀「提醒排程」，判斷現在該不該發、用群組還是私訊，送出後寫「發送紀錄」。

為什麼用 Sheets ＋ Apps Script，而不是正規的後端

考量Sheets ＋ Apps Script一般後端（Cloud Run ＋ DB）
成本$0，公司 Workspace 已包含小，但不是零；要有人管帳單
後台 UI試算表本身就是 CRUD 介面，還有權限、版本紀錄要另外寫管理介面
維運沒有伺服器、沒有 OS 要更新要部署、監控、更新相依套件
代價拿不到 HTTP header（無法驗簽）、觸發器最細 1 分鐘、執行時間上限 6 分鐘完整控制

對 15 人、一天一則的量，代價都在可接受範圍內；唯一真正要處理的是「無法驗簽」，見 ⑧。

03

資料模型：五個分頁

每個分頁第一列是表頭，由選單「1. 建立表格」（setupSheets()）建立。程式用欄位位置讀寫，所以表頭順序就是 schema。

分頁欄位誰寫用途
成員名單稱呼、LINE 名稱、系統編號、好友、在群組、報到時間webhook ＋ 人工補「稱呼」把人看得懂的名字（「小明」）對應到 LINE 的 userId
提醒排程啟用、開始日、結束日、要 @ 誰、提醒內容、時間、群組 @ 的日子、私訊的日子、備註人工一週一列。日子欄接受「一」「二~五」「一、三、五」「每天」
停發日期日期、原因人工國定假日整天不發
設定項目、值（群組 ID、群組名稱）webhook機器人被拉進群組時自動記下 groupId
發送紀錄時間、方式、對象、內容、結果、說明、Request ID、識別碼排程稽核紀錄，同時也是去重依據（見 ⑦）
設計原則：機密不進試算表。Channel ID / secret 放在 Apps Script 的 Script Properties。只有檢視權限的同事看不到它們；但綁定在試算表上的 Apps Script 會繼承試算表的權限，有編輯權的人可以打開專案設定看到 Script Properties。所以試算表的編輯權只給必要的人，一般同事給檢視權就好。
04

排程路徑：每 5 分鐘的一次掃描

runReminders() 是一個無狀態的 reconcile loop：每次都從試算表重新讀全部資料，算出「現在應該已經發但還沒發的」，發掉它，記下來。

  1. 拿鎖。LockService.getScriptLock().tryLock(30s)，拿不到就直接 return。避免前一輪還沒跑完、下一輪又開始，結果重複發。
  2. 今天停發嗎？今天在「停發日期」裡就整輪結束。
  3. 讀今天已發過的識別碼。從「發送紀錄」挑出今天的 key，組成 set。
  4. 逐列判斷。對每個有勾「啟用」的排程列： 
    key = today | 要@誰 | 內容 | 時間        // 今天這一列的唯一識別
if (sentToday[key]) skip
if (!isDue(row, today, nowMinutes)) skip  // 在日期區間內、且 now ∈ [時間, 時間+120 分)
mode = decideMode(row, weekday, everyoneIsFriend)
// 'group' | 'private' | 'group-fallback' | null
  5. 送出並記錄。群組用 textV2 訊息帶 mention；私訊對每個人各 push 一次。結果（含 LINE 回傳的 x-line-request-id）寫進「發送紀錄」。

decideMode 的決策表

今天落在所有對象都是好友？結果則數（15 人群組）
群組 @ 的日子不看group 在群組 @15
私訊的日子是private 私訊每個對象對象人數（通常 1）
私訊的日子否（或對象是「全部人」）group-fallback 改在群組 @，紀錄寫明原因15
都不是—不發0

為什麼是「時間到了之後的 2 小時內」而不是「剛好等於」

Apps Script 的 time-driven trigger 不保證準時，5 分鐘的觸發器實際間隔會飄。用區間判斷 + 已發紀錄去重，可以容忍觸發器延遲或漏跑一輪。超過 120 分鐘就放棄，避免下午 4 點的「下班前記得倒垃圾」在晚上 8 點才送到。

群組 @ 的訊息格式

LINE 的 textV2 用 placeholder 做 mention，使用者內容裡的大括號要跳脫成 {{ }}，否則會被當成 placeholder 而送出失敗。一則最多 @ 20 人。

{
  "type": "textV2",
  "text": "{m0}\n本週值日生，每天下班前記得：倒垃圾、關窗戶",
  "substitution": {
    "m0": { "type": "mention", "mentionee": { "type": "user", "userId": "U…" } }
  }
}
05

Webhook 路徑：讓機器人認得每個人

LINE 的 userId 是每個官方帳號各自不同的不透明字串，沒辦法事先知道。所以必須讓使用者跟機器人「互動一次」，機器人才拿得到他的 ID。這就是「報到」的用途。

事件觸發時機程式做什麼
join機器人被拉進群組反查群組資訊 → 記下群組 ID、群組名稱 → 回覆使用說明
message「報到」有人在群組打「報到」反查群組成員資料 → 檢查是否為好友 → 寫入／更新成員名單 → 回覆「✅ 報到完成」
follow有人加機器人好友反查個人資料 → 成員名單「好友」改 ✅
unfollow有人封鎖／刪除好友確認真的不是好友 → 改 ❌（之後私訊日會自動退回群組 @）
memberJoined新同事進群組回覆提醒他報到
memberLeft / leave有人離開／機器人被踢反查確認後更新狀態

人工只需要在「成員名單」補一欄稱呼，排程表就能用「小明」而不是 Uxxxxxxxx… 來指定對象。

計費模型：為什麼不每天在群組 @

LINE 官方帳號免費方案每月 200 則。push 到群組時，群組裡有幾個人就算幾則；push 給個人算 1 則；reply（回覆使用者訊息）免費。下面可以自己調調看：點一下切換「不發 → 群組 → 私訊」。

群組 算 N 則　私訊 算 1 則　一個月以 4.33 週計

每月估計用量
0

目前採用的「週一群組、週二到週五私訊」約 80～90 則／月（看當月有幾個週一），留了一半以上的空間給 fallback（有人沒加好友時改群組 @）和偶爾的測試訊息。

07

冪等與並行：怎麼確保不會重複發

「提醒發了兩次」是這類系統最常見、也最惹人厭的 bug。這裡疊了四層防護，各自處理不同的失敗情境：

層機制防的是
1Script Lock：runReminders 和 upsertMember 都先拿鎖觸發器重疊執行；同時有多人報到，寫入成員名單時互相覆蓋
2發送紀錄當 outbox：today|對象|內容|時間 寫入「識別碼」欄，每輪先讀出來比對同一列在 2 小時的區間內被每 5 分鐘重送
3X-Line-Retry-Key：每次 push 帶一個 UUID，遇到 5xx 或網路錯誤時用同一把 key 重試；LINE 回 409 代表「這把 key 已經處理過」，視為成功請求其實送到了，但回應在路上掉了，重試導致重複
4webhook 事件去重：用 webhookEventId 放進 CacheService 6 小時LINE 重送同一個 webhook 事件
一個刻意的細節：時間格式錯誤、找不到成員這類設定錯誤也會寫一筆 key 進紀錄。否則同一個錯誤每 5 分鐘會寫一次 log，兩小時就洗出 24 列。
08

安全取捨：無法驗簽，就改成反查

⚠️ 限制：Apps Script 的 doPost(e) 拿不到 HTTP request header

LINE 會在 x-line-signature header 放 HMAC-SHA256 簽章，正規做法是用 channel secret 驗證 body。但 Apps Script Web App 的事件物件不提供 header，所以這一步做不到。Web App 又必須設成「所有人可存取」，LINE 才打得進來。

也就是說，任何知道網址的人都能 POST 偽造事件進來。補強方式是：webhook 不信任事件內容，每一件要寫入狀態的事都先用自己的 token 向 LINE API 反查。

偽造的事件反查結果
假 join，想把群組 ID 換成別的GET /v2/bot/group/{id}/summary機器人不在那個群組 → 失敗，不寫入
假「報到」，想塞假成員GET /v2/bot/group/{id}/member/{userId}，且群組 ID 要等於已記住的那個不是群組成員 → 失敗
假 follow / unfollowGET /v2/bot/profile/{userId}以 LINE 回傳的真實好友狀態為準

剩下的風險：攻擊者可以讓機器人回覆訊息（reply token 是假的，所以實際上會失敗），或消耗 Apps Script 的執行配額。對一個內部工具來說可以接受。

憑證：用 stateless channel access token

不存長期 token。每次需要時用 Channel ID + secret 向 /oauth2/v3/token（client credentials）換一個 15 分鐘有效的 token，在 CacheService 快取 10 分鐘。好處是沒有長期有效的 token 可以外洩，也不需要排程去輪替 token。

09

測試與部署

測試

純邏輯（parseWeekdays、parseTime、decideMode、isDue、buildGroupMessage）寫成不依賴 Google API 的函式，用 Node 內建的 node:test 測。流程測試把 SpreadsheetApp、UrlFetchApp 等全域物件 mock 掉，在 Node 的 vm 裡跑整支 Code.gs，驗證「私訊日有人沒加好友 → 改群組 @」「同一天不重複發」這類情境。共 21 項。

部署

貼上 Code.gs → 部署成 Web App（執行身分：擁有者；存取：所有人）→ 網址填到 LINE Developers 的 Webhook URL。之後改程式要用「管理部署作業 → 編輯 → 新版本」，網址才不會變，LINE 那邊不用重設。

已知限制

  • 準確度 ±5 分鐘：受限於觸發器間隔。對「下班前提醒」來說夠用。
  • 只用電腦版 LINE 的人：如果從沒在手機上同意過資料分享，webhook 事件裡沒有 userId，機器人會請他改用手機報到。
  • Sheets 當資料庫：「發送紀錄」會一直長，每輪都全表掃描。以一天幾列的量，幾年內都不是問題；真的變慢再改成只讀最後 N 列。
  • 單一群組：設定只記一個群組 ID。要支援多群組，排程表要多一欄「發到哪個群組」。
